Guía de la API

Demo local sin autenticación. Base: http://127.0.0.1:3000. Las peticiones con cuerpo usan Content-Type: application/json. Trabaja con datos ficticios.

1. Crear una solicitud

{
  "title": "No puedo descargar un reporte",
  "description": "La descarga se detiene al llegar al final.",
  "category": "functionality"
}

Título: 5–120 caracteres. Descripción: 10–5000. Categorías: functionality, data y usage. Se recortan espacios exteriores y se cuentan puntos de código Unicode. No se permiten campos extra. UUID, fecha, solicitante ficticio y estado inicial se asignan en el servidor.

2. Consultar y buscar

GET /tickets?q=reporte&status=open&page=1&limit=20

Filtros opcionales: q (2–120 caracteres), status, category, priority, assignee, createdFrom y createdBefore. page admite 1–10000; limit, 1–100. Por defecto: página 1 y límite 20. El listado está ordenado del más reciente al más antiguo. Una página sin resultados devuelve una lista vacía.

Las fechas usan AAAA-MM-DD en UTC: createdFrom incluye el día y createdBefore lo excluye. Los filtros inválidos o repetidos devuelven 400. El parámetro q busca texto literal en título y descripción sin distinguir mayúsculas.

3. Registrar atención y solución

PATCH /tickets/:id/status
{
  "expectedVersion": 1,
  "expectedStatus": "open",
  "status": "in_progress",
  "reason": "Se inicia la revisión de la descarga."
}

Flujo: open → in_progress → resolved. Para resolver, usa expectedStatus in_progress y status resolved. El motivo es obligatorio, de 10–2000 caracteres. Estado e historial se guardan en una transacción. expectedVersion debe coincidir con version obtenido al consultar el ticket. Desde resolved puedes reabrir a in_progress o cerrar a closed; closed es definitivo. Los historiales admiten page y limit. Ante un 409, consulta el ticket de nuevo antes de decidir el siguiente cambio.

4. Conversar

POST /tickets/:id/comments
{ "body": "El problema ocurre con el reporte mensual." }

Solo se acepta body, de 1–5000 caracteres. La consulta admite page y limit y devuelve mensajes del más antiguo al más reciente. Un ticket cerrado rechaza comentarios con 409. Se permite comentar tickets resueltos; los comentarios no cambian el estado. Todos usan el autor ficticio local-demo-user. Renderiza los mensajes como texto, nunca como HTML.

5. Medir la atención

GET /metrics/tickets?category=data&createdFrom=2026-10-01&createdBefore=2026-11-01

Cuenta el estado actual de los tickets creados en el periodo. No admite q, status ni paginación. resolution.averageSeconds mide creación hasta última resolución entre tickets actualmente resueltos o cerrados con fechas válidas. sampleSize es la muestra y excludedCount los resueltos sin duración válida. Sin muestra, averageSeconds es null. No mide horas laborales ni confirma satisfacción del solicitante.

6. Prioridad y responsable

GET /agents devuelve agentes ficticios. La prioridad inicial es normal; las opciones son low, normal, high y urgent. Los filtros de prioridad y responsable solo afectan la bandeja. assignee=unassigned busca tickets sin asignar.

PATCH /tickets/:id/management
{
  "expectedVersion": 1,
  "kind": "priority",
  "value": "high",
  "reason": "El problema bloquea el trabajo del solicitante."
}

Para asignar usa kind assignment y value demo-agent-1, demo-agent-2 o null. Responde 204, o 409 si está cerrado, la versión cambió o el valor es el mismo. GET /tickets/:id/management-history devuelve data y pagination con cambios y motivos. Los motivos admiten 10–2000 caracteres; no se aceptan campos extra. Estas operaciones no tienen permisos reales en la demo.

Errores y límites

Los errores devuelven {"error":"mensaje"} o {"error":{"field":"campo","message":"mensaje"}}. Un fallo interno devuelve 500 sin detalles de PostgreSQL. El texto NUL o Unicode malformado se rechaza. No hay autenticación, permisos, edición, borrado, adjuntos ni cierre automático. Estas rutas son para uso local.

Ejemplos ejecutables: docs/demo.ps1 en el repositorio.
